# H5 性能优化：指标、诊断与验证笔记

> 选题参考 Niuhk 的[性能诊断和优化手段](https://niuhk.cn/2022/07/22/前端性能优化%28三%29-性能诊断和优化手段/)。本文以一个假设的活动页为例整理排查步骤，指标口径参考官方文档；文中的优化路径不是线上实测结果。

相关笔记：[HTTP](../http/http.md) · [WebView 离线包](../hybrid/offline-package.md) · [内存排查](../javascript/memory-diagnostics.md)

## 1. 核心认识：先把“慢”翻译成可测的问题

用户说页面慢，可能是打开后很久没有内容、点击后按钮没反应，也可能是布局不断移动。这三类问题的根因不同。

| 体验 | 关注指标 | 良好体验参考值 |
| --- | --- | --- |
| 主要内容出现慢 | LCP：最大内容绘制 | 不超过 2.5 秒 |
| 交互响应慢 | INP：交互到下一次绘制 | 不超过 200 毫秒 |
| 布局不稳定 | CLS：累积布局偏移 | 不超过 0.1 |

这些是 Core Web Vitals 的参考阈值，通常按移动端和桌面端分别看真实访问的第 75 百分位。三项都达标才算整体通过；不能用一次本地测量代替用户分布。[Web Vitals](https://web.dev/articles/vitals)

“白屏结束”“业务首屏完成”“点击到弹窗展示”可以额外定义，但必须写清起止点。FCP 只说明已有内容绘制，不保证关键接口和主要内容都准备好。

## 2. 问题场景：一个活动页打开慢

假设页面包含首图、用户状态接口、规则弹窗和下方推荐列表。先画关键路径：

```text
导航 → HTML → 脚本下载/执行 → 接口 → 首图与文案展示
                          └→ 非首屏推荐列表
```

先问：哪个等待真正阻塞了用户看到主要内容？例如主图地址必须等接口返回，就算图片 CDN 很快，也会被接口串行依赖拖住。此时只压缩脚本体积可能收益有限。

## 3. 实现要点：采集和诊断分开做

**真实用户监控**回答“哪些用户受影响”；**实验室复现**回答“具体哪一步耗时”。前者适合判断范围，后者适合分析调用栈、网络瀑布和渲染过程。

浏览器工程中安装 `web-vitals` 后，可从开发环境日志开始：

```ts
import { onCLS, onINP, onLCP } from 'web-vitals'

function recordMetric(metric: {
  name: string
  value: number
  id: string
  rating: string
}) {
  // 开发期先核对事件，再接入自己的同源采集接口。
  console.table({
    name: metric.name,
    value: metric.value,
    id: metric.id,
    rating: metric.rating,
  })
}

onCLS(recordMetric)
onINP(recordMetric)
onLCP(recordMetric)
```

部分指标要到交互发生或页面生命周期变化时才有结果，没有日志不一定是初始化失败。正式接入时还需处理抽样、上报失败及同一指标 ID 的更新，不能把每次回调当成一条独立访问。[web-vitals 项目文档](https://github.com/GoogleChrome/web-vitals)

建议附带路由模板、发布版本、设备类别和必要的网络维度。不要直接记录带用户信息的完整 URL 查询参数。

## 4. 诊断顺序：先网络，再主线程，再渲染

| 观察到的现象 | 下一步证据 | 可能的改进方向 |
| --- | --- | --- |
| HTML 很晚返回 | 导航请求的等待时间、服务端耗时 | 缓存、服务端处理、网络链路 |
| 主图开始请求很晚 | 请求发起者、依赖关系 | 减少串行依赖，提前暴露资源地址 |
| 脚本下载完仍白屏 | Performance 中长任务与执行栈 | 拆分非关键初始化、延迟非首屏功能 |
| 点击时卡住 | 交互附近的计算与布局任务 | 减少同步工作，拆任务，必要时使用 Worker |
| 内容突然下移 | Layout Shift 记录 | 为图片、广告位和异步模块预留空间 |

使用 Chrome DevTools 的 Performance 面板录制具体操作，查看主线程任务和相关事件，再回到代码验证原因。[Performance 文档](https://developer.chrome.com/docs/devtools/performance)

优化实验一次只改变一个主要因素。否则即使变快，也不知道是哪项改变生效，出了兼容问题更难回滚。

## 5. 优化不是一张通用开关表

**懒加载**适合非首屏资源；把首屏主图也懒加载，反而可能延迟展示。

**缓存**必须配合更新规则：带内容哈希的静态文件可以长缓存；HTML 和业务数据需要各自的失效策略。缓存命中率高不代表内容一定正确。

**预加载**应服务于明确的关键资源。把所有资源都预加载，会让非关键请求争抢带宽。

**骨架屏**能提供等待反馈，但不代表业务数据更早可用。它还应预留稳定尺寸，避免加载完发生明显跳动。

**离线包**可以减少部分资源网络等待，但仍有包下载、版本匹配、容器初始化、解压和数据请求的成本。方案边界见[离线包笔记](../hybrid/offline-package.md)。

## 6. 验证：同时比较收益和副作用

发布前固定页面版本、测试设备、网络条件和操作步骤，分别测冷缓存与热缓存。重复测量后比较分布，不挑最快的一次当成果。

发布后观察相同用户分组的指标变化，并同时检查错误率、资源失败、页面功能和内存。若只看加载时间，可能把“代码没有执行导致变快”误认为优化成功。

对业务首屏的自定义测量，可以用 `performance.mark()` 和 `performance.measure()` 标记同一流程的起止点。必须说明标记发生在数据到达、DOM 更新还是实际绘制阶段；命名为 `data-ready` 的点不能直接当作“用户已经看见”。

## 7. 易错点与学习自检

- **把平均值当全部用户体验**：平均值可能隐藏低端机和弱网用户的长尾。
- **把 TBT 当 INP**：实验室阻塞时间和真实交互响应衡量的不是同一件事。
- **照搬 DNS 优化收益**：解析时间受缓存和网络环境影响，固定“省多少毫秒”不能通用。
- **认为 transform 必定更快**：合成层也有成本，需要观察实际渲染结果。
- **只测桌面浏览器**：App WebView、字体缩放和设备资源都可能改变表现。

自检：如果主图加载很快但 LCP 仍慢，你会检查哪个时间段？如果本地分数提高但线上 p75 没变，你会如何检查样本与测试条件？
