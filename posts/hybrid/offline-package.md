# WebView 离线包：更新、校验、灰度与回退笔记

> 参考 Niuhk 的 [H5 离线包方案](https://niuhk.cn/2023/09/05/H5离线包方案/)，补充状态转换和异常场景。下文是通用架构设计笔记，不是某个客户端已实现的接口规范。

相关笔记：[H5 性能优化](../performance/h5-performance.md) · [HTTP 缓存](../http/http.md)

## 1. 核心认识：资源可离线，业务不一定可离线

离线包通常把 HTML、JavaScript、CSS 和部分静态资源提前下载到客户端。WebView 打开页面时优先使用本地资源，减少关键路径上的网络等待。

它不自动解决登录、实时数据、服务端接口和首次下载。客户端在 WebView 创建前预取业务数据，是可以组合的优化方式，并非所有离线包必须这样做。

| 机制 | 由谁管理 | 主要作用 |
| --- | --- | --- |
| HTTP 缓存 | 浏览器与服务端缓存策略 | 复用响应、减少传输 |
| Service Worker 缓存 | Web 应用及浏览器生命周期 | 拦截请求、实现 Web 离线策略 |
| App 离线包 | 原生客户端与发布平台 | 预下载资源、管理版本及本地加载 |

Service Worker 的注册、激活和缓存更新有自己的生命周期，不能直接等同于原生离线包。[MDN：使用 Service Worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers)

## 2. 问题场景：新包下载了一半，用户打开页面

如果直接覆盖旧目录，新 HTML 可能引用尚未下载的新 JS，或者仍拿到旧 CSS。此时下载成功率再高，也会出现难复现的版本混用。

更可靠的设计是让包经历明确阶段：

```text
发现版本 → 下载到临时目录 → 校验 → 解压并检查资源
→ 标记可用 → 原子切换当前版本

任何阶段失败 → 保留旧可用版本 → 上报原因 → 按策略重试或走线上
```

新包完整可用之前，当前版本不变。已打开的页面固定使用同一版本，避免页面运行中切换一半资源。

## 3. 实现要点：清单承担版本契约

下面是教学用清单，哈希和签名由发布工具生成，客户端必须校验真实值，不能把占位文字当作有效配置。

```json
{
  "appId": "demo-activity",
  "version": "2026.09.16.1",
  "entry": "index.html",
  "minContainerVersion": "2.0.0",
  "archiveUrl": "https://cdn.example.com/demo-activity/2026.09.16.1.zip",
  "archiveSha256": "由发布工具填入实际摘要",
  "signature": "由发布工具填入实际签名",
  "files": ["index.html", "assets/app.js", "assets/app.css"]
}
```

版本号用于定位内容，容器最低版本用于判断兼容性，入口和资源列表用于完整性检查。还应明确签名覆盖哪些字段、如何序列化、使用哪个可信公钥验证。

**摘要与签名职责不同：**摘要可以发现内容与预期不一致；如果摘要和包一起被替换，就不能仅靠摘要证明发布者身份。签名需要建立在可信密钥和明确验证流程上。

## 4. 安装过程要考虑失败和恢复

可将下载、安装与激活分成三个独立步骤：

1. **下载**：限制包大小、总超时和重试次数；失败不影响当前版本。
2. **安装**：验证签名与摘要，解压到版本目录，检查入口和必需资源。
3. **激活**：持久化可用状态，再切换版本指针；清理历史包时保留正在使用的版本。

解压时还需要防止路径越界和异常膨胀。更新进程被中断后，客户端启动应能识别未完成的临时目录，并重新开始或恢复，不要把它标记成正式版本。

增量包必须绑定准确的基线版本。合并失败时回退到完整包，不能把部分合并结果发布为成功。

## 5. WebView 如何加载本地资源？

客户端需要把页面 URL 与包内资源建立映射，同时维持可预期的来源规则。Android 官方提供 `WebViewAssetLoader`，用于通过 HTTP(S) 风格 URL 加载应用内内容，可作为理解本地资源加载的入口。[Android：加载应用内内容](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content)

这只是平台机制，不等于已经有完整离线包平台。iOS 与 Android 的容器实现、请求拦截和来源限制需要分别设计、分别验证。

对单个缺失文件直接回源，可能混入另一版本的资源。若允许这种策略，线上地址必须能锁定同一包版本；否则应考虑整个页面回退到一致的线上版本。

## 6. 灰度和回退：不是随机放行就结束

灰度建议按稳定用户或设备分组，让同一个对象在观察周期内命中一致版本。服务端记录包版本、容器版本与分组，客户端记录实际使用结果。

至少要能区分：

- 下载成功率：网络和分发是否正常。
- 安装成功率：校验与解压是否正常。
- 离线命中率：真正打开时是否用了可用本地包。
- 页面可用性：脚本、接口和关键交互是否成功。
- 首屏与错误率：新版本是否真的改善体验。

“包已下载”不代表“页面命中离线包”，更不代表“页面正常”。达到回退条件时，可切回前一个稳定版本或线上模式，但业务接口也要兼容回退版本。

## 7. 易错点与学习自检

| 场景 | 设计时应回答的问题 |
| --- | --- |
| 首次启动没有包 | 走线上，还是展示等待？等待有多长？ |
| 下载中断 | 当前可用包是否仍能打开？ |
| 磁盘空间不足 | 是否停止安装、保留旧包并反馈？ |
| 容器版本太旧 | 是否拒绝激活不兼容的新包？ |
| 增量合并失败 | 是否能退回完整包？ |
| 新包接口不兼容 | 回退资源后，业务是否仍然正常？ |

自检：为何需要临时目录和原子切换？为什么下载成功不能作为离线优化的唯一指标？如果只回源一个缺失 JS，怎样保证版本一致？
